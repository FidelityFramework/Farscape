# Boundary Marshaling Specification

## The Rule

**No C idioms may appear in Layer 3 or application code.** Layer 2 is the membrane — C goes in one side, Clef comes out the other. Nothing from C crosses the membrane except through explicit marshaling into Clef-native types and patterns.

This rule extends beyond type names (the original `boundary_marshaling.md` scope) to cover the full surface of C pollution: types, memory idioms, resolution idioms, pointer patterns, and string conventions.

## Layer Model

| Layer | Generated By | Contains C Idioms? | Consumer |
|---|---|---|---|
| **Layer 1** — FidelityExtern declarations | Farscape | Yes — raw C types in signatures | Layer 2 only |
| **Layer 2** — Idiomatic wrappers, protocol marshaling, callback builders | Farscape | Yes — this IS the membrane | Layer 3 |
| **Layer 3** — Composition libraries | Developer | **No — pure Clef** | Application code |

> **Two caveats added 2026-08-03.**
>
> **Layer 3 is a convention, not a mechanism.** `Layer3` is a declared type in
> `PilotTypes.fs` and is set to `None` at every construction site;
> `PilotAnalyzer.analyzeLayer3Requirements` runs only on the protocol and callback paths.
> Nothing enforces the prohibitions below. They are discipline for a developer writing an
> overlay by hand.
>
> **This table specifies idiom containment and says nothing about representation.** That
> gap is load-bearing: a handle expressed as a Clef record satisfies every rule in this
> document and still reaches a C callee as the address of a slot rather than as the handle,
> because records are memref-backed. See `docs/14_Binding_Generation_Gaps.md` §3 and §7.
> The correct Layer 1 output for a pointer typedef is bare `nativeint`, which §4 below
> currently reads as a violation. A future revision of this document should gain a
> Representation section rather than a sibling document being created.
| **Application** — end-user programs | Developer | **No — pure Clef** | End user |

Layer 2 includes:
- Wrapper functions (`*Api.clef`) — error handling, nullable wrapping, typed returns
- Protocol dispatch (`ProtocolDispatch.clef`) — argument packing, interface resolution, marshal calls
- Callback builders (`Callbacks.clef`) — dlsym resolution, listener struct construction

All of these are **generated by Farscape** and contain C idioms by design. They are the membrane.

## What Must Not Appear in Layer 3

### 1. No C Type Names (existing rule)

C type names (`hipError_t`, `resvg_error`, `wl_interface`) must not appear in generated Clef code. Error functions take `int32`. Results are `Result<T, string>`.

| C Concept | Wrong | Right |
|---|---|---|
| Error enum | `code: hipError_t` | `code: int32` |
| Pointer return | `option<nativeint>` with C null semantics | `Result<nativeint, string>` via NullWithReason |
| Error result | `Result<unit, hipError_t>` | `Result<unit, string>` |

### 2. No C Memory Idioms

Layer 3 code must not call `malloc`, `free`, or use `NativePtr` directly. Memory management for C interop buffers is contained within Layer 2.

| Pattern | Wrong (Layer 3) | Right (Layer 3) |
|---|---|---|
| State buffer | `malloc 24` → `NativePtr.set` → pass → `NativePtr.get` → `free` | Call L2 function that returns a typed record |
| Arg packing | `NativePtr.ofNativeInt` → `NativePtr.set` per field | Call L2 function with typed parameters |
| Handle unpacking | `NativePtr.get handlesPtr 0` | Access record field: `connection.Display` |

### 3. No C Resolution Idioms

Layer 3 code must not call `dlsym` or `strcmp`. Symbol resolution and string-based dispatch are contained within Layer 2.

| Pattern | Wrong (Layer 3) | Right (Layer 3) |
|---|---|---|
| Interface global | `dlsym 0n "wl_compositor_interface"` | L2 resolves internally (or extern data declaration) |
| Callback symbol | `dlsym 0n "MyModule.handler"` | L2 callback builder accepts symbol name |
| Protocol name match | `strcmp iface "wl_compositor"` | L2 registry wrapper handles dispatch |

### 4. No Raw Pointer Signatures

Layer 3 function signatures use typed records, discriminated unions, Options, and Results. `nativeint` and `nativeptr<T>` appear only in Layer 1 and Layer 2.

| Pattern | Wrong (Layer 3 signature) | Right (Layer 3 signature) |
|---|---|---|
| Connection result | `connect () : nativeint` | `connect () : DisplayConnection option` |
| Handle parameter | `createSurface (compositor: nativeint)` | `createSurface (compositor: WaylandCompositor)` |
| Callback data | `registryGlobal (data: nativeint)` | Closure captures state; no data parameter at L3 |

### 5. No C String Patterns

Layer 3 code must not use `.Pointer` to obtain C string pointers, or pass `nativeptr<byte>` for string arguments. Layer 2 wrappers accept Clef `string` values and marshal internally.

## The Static Binding Elision Test

Every dynamic binding pattern must answer: **"What happens when this library is statically linked?"**

If a pattern requires runtime `dlsym` to function, but the symbol could be resolved at link time via a `[<FidelityExtern>]` declaration, the pattern has unnecessary runtime overhead that static binding would eliminate. The architecture should ensure that switching from dynamic to static linking requires **changing the link strategy, not the source code**.

| Pattern | Dynamic Binding | Static Binding | Elides Cleanly? |
|---|---|---|---|
| `[<FidelityExtern>]` function | Linker resolves via .so | LTO resolves via .a | Yes |
| `[<FidelityExtern>]` data symbol | Linker resolves global | LTO resolves global | Yes (requires extern data support) |
| Callback via closure code_ptr | Runtime dispatch | Direct call | Yes (requires closure-to-fnptr) |
| Callback via `dlsym(symbolName)` | Runtime lookup | Direct function pointer | Yes (if closures replace dlsym) |
| Interface global via `dlsym` | Runtime lookup | Link-time resolution | Yes (if extern data replaces dlsym) |
| State via closure captures | Stack/arena allocation | Same | Yes |
| State via malloc'd buffer | Manual lifecycle | N/A — wrong pattern | No — does not elide |

**Principle**: If a dynamic binding pattern has no clean static equivalent, it is an architectural smell. The binding declaration should be the same for both; only the link strategy changes.

## Extern Data Declarations (Roadmap)

C libraries export global data symbols (e.g., Wayland's `wl_compositor_interface`). Today these are resolved via `dlsym` at runtime. The principled approach is a `[<FidelityExtern>]` variant for data symbols:

```clef
// Layer 1 — extern data declaration (roadmap)
[<FidelityExtern("wayland-client", "wl_compositor_interface")>]
let wl_compositor_interface : nativeint = NativeDefault.zeroed ()
```

This resolves at link time (dynamic or static) without runtime `dlsym`. The Layer 2 protocol dispatch code uses it directly. Layer 3 never sees it.

**Compiler requirement**: Alex must emit MLIR extern global declarations for data symbols, distinct from function declarations.

## Closure Roadmap for Callbacks

The current callback mechanism uses top-level Clef functions with C calling convention, resolved via `dlsym` by name. State passes through the `data: void*` pointer as a malloc'd buffer.

The target state uses flat closures: the closure's `code_ptr` becomes the callback function pointer, and the closure struct (carrying captured state) becomes the `data` pointer. The structural parallel is exact — both patterns pass an opaque pointer as the first argument carrying state.

| Aspect | Today (dlsym) | Target (closures) |
|---|---|---|
| Function resolution | `dlsym(RTLD_DEFAULT, "Module.handler")` | Closure `code_ptr` extracted at call site |
| State passing | `malloc` buffer → `NativePtr.set` → `data` void* | Closure struct → `&closure` as first arg |
| State access | `NativePtr.get` on `data` pointer | `extractvalue` on closure struct |
| Lifecycle | Manual `malloc`/`free` | Stack or arena (escape analysis) |
| Static elision | Requires `-rdynamic` or explicit export | Direct — no runtime symbol lookup |

**Principle**: The Layer 2 API surface (callback builders, listener constructors) should be the same whether the underlying mechanism is dlsym or closures. Only the Layer 2 internals change. Layer 3 code is unaffected.

## The Binding-Port Spectrum

From the MFEM roadmap: libraries exist on a spectrum from pure binding (opaque service) to full port (algorithm re-expressed in Clef).

| Library | Product | Boundary Implication |
|---|---|---|
| libdrm, libgbm | Binding | C stays outside membrane; L2 marshals; L3 is pure Clef |
| ROCm/HIP | Binding | Same — opaque GPU runtime |
| Wayland | Binding | Same — protocol dispatch is L2 |
| DuckDB (static) | Binding | Same declaration, static link strategy |
| MFEM mesh I/O | Binding | Combinatorial; IEEE adequate |
| MFEM kernels | Port | C ingested and re-expressed; membrane dissolves |

For **bindings**: the boundary spec is enforced at Layer 2. C never leaks past.

For **ports**: there is no C to leak — the algorithm is re-expressed in Clef. But during partial porting (transition period), the boundary spec ensures that ported code remains pure Clef even while unported components are consumed via binding.

## Verification Checklist

For any Farscape-generated library:

- [ ] Layer 1 files contain only `[<FidelityExtern>]` declarations with `NativeDefault.zeroed()` bodies
- [ ] Layer 2 files may contain `dlsym`, `malloc`, `NativePtr`, `nativeint` — they are the membrane
- [ ] Layer 2 wrapper signatures expose Clef-native types (`Result<T, string>`, `Option<T>`, typed records)
- [ ] No Layer 3 file imports `Fidelity.Libc.DynamicLink` or `Fidelity.Libc.Memory` for interop purposes
- [ ] No Layer 3 file uses `NativePtr.*` operations
- [ ] No Layer 3 function signature contains `nativeint` or `nativeptr<T>`
- [ ] No application file uses any of the above
- [ ] Generated comments correctly classify each file's layer
- [ ] Every `dlsym` call has a documented path to extern data or closure replacement
