# Library Verification Pipeline

## Purpose

Farscape generates Clef source libraries from C headers. These libraries are consumed by Composer (via CCS type-checking) and must be **verified error-free** before they can be trusted within the Fidelity Framework ecosystem. Library verification serves two goals:

1. **Correctness gate**: Confirm that generated bindings type-check cleanly under CCS with zero errors. Type mismatches (e.g., `int32` vs `int`, missing NTU mappings, incorrect Option usage) are real bugs that must be fixed in the generation pipeline.

2. **Future clefpak packaging**: A verified library is a candidate for `clefpak` — a signed, compressed source artifact for the Fidelity package management system. Verification is the prerequisite for packaging.

---

## The Problem

CCS performs reachability analysis on the PSG after type-checking. Diagnostics on nodes not reachable from the application's entry point are demoted from `Error` to `Info` severity. This means:

- A library with type errors **appears clean** when compiled as a dependency, because no application code has `open`ed its modules yet.
- The moment application code reaches for a binding in that library, the errors surface as hard blockers.
- This creates a false sense of confidence in generated bindings.

Library verification must process bindings **as if all modules are reachable**, bypassing the severity demotion that occurs when the library is merely a transitive dependency.

---

## Design

### `farscape verify` Command

```
farscape verify --fidproj <path-to-fidproj>
```

Invokes CCS against the library's fidproj to type-check all source files. Reports diagnostics at their **true** severity (not demoted by reachability).

**Inputs**:
- A `.fidproj` file (generated by Farscape or hand-authored)
- The library's source files (Layer 1 + Layer 2 + optional Overlay)

**Outputs**:
- Pass/fail status
- Diagnostic listing with file, line, severity, message
- Summary: error count, warning count

**Exit codes**:
- `0`: All sources type-check with zero errors
- `1`: Type errors found (listing printed to stderr)
- `2`: Infrastructure error (CCS unavailable, fidproj not found, etc.)

### Integration with Generation Pipeline

When `farscape project --project <pilot.toml> --wrappers` generates a library, the verification step can be chained:

```
farscape project --project pilot/stb_image.pilot.toml --wrappers
farscape verify --fidproj CPU/Linux/x86_64/Fidelity.Image.Stb.fidproj
```

A future `--verify` flag on `farscape project` could make this automatic.

### Feedback Loop

Verification failures indicate bugs in Farscape's code generation, not in the C headers. The remediation cycle:

1. `farscape project` generates bindings
2. `farscape verify` reports type errors
3. Developer (or CI) investigates: is this a TypeMapper gap? A wrapper pattern edge case? A missing NTU mapping?
4. Fix is applied to Farscape's generation pipeline (TypeMapper.fs, WrapperCodeGenerator.fs, etc.)
5. Regenerate and re-verify until clean

This cycle matures the binding generation process over time. Each fix addresses a class of C API patterns, not just one library.

## Known Type Issues (March 2026)

Current generation produces these classes of CCS type errors:

| Issue | Root Cause | Fix Location |
|-------|-----------|--------------|
| `int32` vs `int` mismatch | C `int` mapped to `int32` but some NTU contexts expect `int` (platform word) | TypeMapper.fs — ensure consistent Fixed-width mapping |
| `Option` type constructors | Generated code uses Option patterns not recognized by CCS | WrapperCodeGenerator.fs — align with NTU Option representation |
| Missing module opens | Generated Layer 2 files reference Layer 1 types without proper `open` | BindingGenerator.fs — emit correct module references |

These are systematic issues. Fixing them in the generator fixes all libraries simultaneously.

## Relationship to clefpak

```
C Headers → Farscape → Generated Clef Source
                              ↓
                        farscape verify (CCS type-check)
                              ↓ (pass)
                        clefpak pack (future)
                              ↓
                        Signed, compressed source artifact
                              ↓
                        Package registry / dependency resolution
```

`clefpak` is the future package format for the Fidelity ecosystem. It contains:
- Verified Clef source (not compiled binaries — Fidelity uses source-based linking)
- Cryptographic signature for provenance
- Metadata: platform target, NTU version, dependency graph

A library cannot be packaged as a clefpak until it passes verification. This is the quality gate.

---

## Source-Based Linking

The Fidelity ecosystem does **not** use binary assemblies. Libraries are source packages:

- Composer's `SourceResolver` walks dependency fidproj files recursively
- `open` statements determine reachability within the PSG
- CCS type-checks all reachable source together in a shared type environment
- No binary ABI compatibility concerns — source is re-checked on every compilation

This means library "compilation" is verification, not artifact production (until clefpak).

---

## fidproj Hierarchy

Farscape generates **one fidproj per pilot TOML invocation**. Library authors compose parent fidproj files at whatever hierarchical level makes sense for their library:

```
Fidelity.Platform/CPU/Linux/x86_64/
  Fidelity.Platform.fidproj           ← hand-authored, composes sub-libraries
  Fidelity.Platform.libc.fidproj      ← generated by Farscape
  Fidelity.Platform.pthread.fidproj   ← generated by Farscape
  Bindings/Libc/...
  Bindings/Pthread/...
```

Each generated fidproj is independently verifiable. Parent fidproj files compose them as dependencies.

## Roadmap

### Near-term
- Implement `farscape verify` command
- Fix known TypeMapper and wrapper generation issues until core libraries pass
- Integrate verification into CI for Farscape's own test suite

### Medium-term
- `--verify` flag on `farscape project` for automatic post-generation check
- Machine-readable diagnostic output (JSON) for CI integration
- Verification status tracking across library versions

### Long-term (Atelier integration)
- Farscape's capabilities fold into Composer's **Transpose** feature (typed dynamic binding)
- Verification becomes part of Composer's library management, accessible through Atelier IDE
- `clefpak` packaging with verification as prerequisite gate
- Full algorithmic port capability via **Transcribe** (beyond FFI binding)
