# Library Verification Pipeline

## Status: Design Phase (verified 2026-08-03)

**`farscape verify` is not implemented.** The CLI root command is
`generate | pilot {analyze,init,discover} | project`; there is no `verify` subcommand. Every
description of the command below — its flags, its exit codes, the shell transcripts, the
remediation cycle — is a specification of intended behaviour written in the indicative.
Read it as a design, not as documentation of a working tool.

Note also that CCS type-checking is a **necessary and insufficient** gate. Four known
classes of binding defect are entirely type-clean and would pass this pipeline once it
exists; see `docs/14_Binding_Generation_Gaps.md` §6.

## Purpose

Farscape generates Clef source libraries from C headers. These libraries are consumed by Composer (via CCS type-checking) and must be **verified error-free** before they can be trusted within the Fidelity Framework ecosystem. Library verification serves two goals:

1. **Correctness gate**: Confirm that generated bindings type-check cleanly under CCS with zero errors. Type mismatches (e.g., `int32` vs `int`, missing NTU mappings, incorrect Option usage) are real bugs that must be fixed in the generation pipeline.

2. **Future clefpak packaging**: A verified library is a candidate for `clefpak` — a signed, compressed source artifact for the Fidelity package management system. Verification is the prerequisite for packaging.

---

## The Problem

CCS performs reachability analysis on the PSG after type-checking. Diagnostics on nodes not reachable from the application's entry point are demoted from `Error` to `Info` severity. This means:

- A library with type errors **appears clean** when compiled as a dependency, because no application code has `open`ed its modules yet.
- The moment application code reaches for a binding in that library, the errors surface as hard blockers.
- This creates a false sense of confidence in generated bindings.

Library verification must process bindings **as if all modules are reachable**, bypassing the severity demotion that occurs when the library is merely a transitive dependency.

## Design

### `farscape verify` Command

```
farscape verify --fidproj <path-to-fidproj>
```

Invokes CCS against the library's fidproj to type-check all source files. Reports diagnostics at their **true** severity (not demoted by reachability).

**Inputs**:
- A `.fidproj` file (generated by Farscape or hand-authored)
- The library's source files (Layer 1 + Layer 2 + optional Overlay)

**Outputs**:
- Pass/fail status
- Diagnostic listing with file, line, severity, message
- Summary: error count, warning count

**Exit codes**:
- `0`: All sources type-check with zero errors
- `1`: Type errors found (listing printed to stderr)
- `2`: Infrastructure error (CCS unavailable, fidproj not found, etc.)

### Integration with Generation Pipeline

When `farscape project --project <pilot.toml> --wrappers` generates a library, the verification step can be chained:

```
farscape project --project pilot/stb_image.pilot.toml --wrappers
farscape verify --fidproj CPU/Linux/x86_64/Fidelity.Image.Stb.fidproj
```

A future `--verify` flag on `farscape project` could make this automatic.

### Feedback Loop

Verification failures indicate bugs in Farscape's code generation, not in the C headers. The remediation cycle:

1. `farscape project` generates bindings
2. `farscape verify` reports type errors
3. Developer (or CI) investigates: is this a TypeMapper gap? A wrapper pattern edge case? A missing NTU mapping?
4. Fix is applied to Farscape's generation pipeline (TypeMapper.fs, WrapperCodeGenerator.fs, etc.)
5. Regenerate and re-verify until clean

This cycle matures the binding generation process over time. Each fix addresses a class of C API patterns, not just one library.

## Known Issues

Defects in generated bindings are catalogued in **`docs/14_Binding_Generation_Gaps.md`**,
which supersedes the table that stood here. That table listed three classes of CCS type
error; its first row stated the `int` mapping backwards — `TypeMapper.fs` maps C `int` to
Clef `int` deliberately, as register-width dimensional and explicitly *not* `int32`, per
`.serena/memories/TYPE_MAPPING_ARCHITECTURE_ANALYSIS.md`. Applying its prescribed fix would
undo that decision.

More importantly, the table's premise was that binding defects surface as type errors. The
four defects now catalogued are all type-clean: a struct dropped by declaration shadowing
produces no node to check; a packed record with wrong offsets checks and reads the wrong
bytes; a memref-backed handle record checks and passes the wrong pointer; a collapsed fixed
array is a valid one-element field. This pipeline cannot detect any of them.

The systematic-fix principle still holds — each generator fix addresses a class of C API
patterns across every library at once. It simply covers a narrower class of defect than this
document originally assumed.

## Relationship to clefpak

```
C Headers → Farscape → Generated Clef Source
                              ↓
                        farscape verify (CCS type-check)
                              ↓ (pass)
                        clefpak pack (future)
                              ↓
                        Signed, compressed source artifact
                              ↓
                        Package registry / dependency resolution
```

`clefpak` is the future package format for the Fidelity ecosystem. It contains:
- Verified Clef source (not compiled binaries — Fidelity uses source-based linking)
- Cryptographic signature for provenance
- Metadata: platform target, NTU version, dependency graph

A library cannot be packaged as a clefpak until it passes verification. This is the quality gate.

---

## Source-Based Linking

The Fidelity ecosystem does **not** use binary assemblies. Libraries are source packages:

- Composer's `SourceResolver` walks dependency fidproj files recursively
- `open` statements determine reachability within the PSG
- CCS type-checks all reachable source together in a shared type environment
- No binary ABI compatibility concerns — source is re-checked on every compilation

This means library "compilation" is verification, not artifact production (until clefpak).

## fidproj Dependency Resolution

### Design Principle: Dependencies Point at fidproj Files

Dependencies specify a **fidproj file**, not a directory. This is explicit, deterministic,
and avoids ambiguity when a directory contains multiple fidproj files alongside non-library
artifacts (pilot TOMLs, Layer 3 overlays, tooling hooks).

```toml
[dependencies]
platform = { path = "../Fidelity.Platform/CPU/Linux/x86_64/Fidelity.Platform.fidproj" }
libc = { path = "../Fidelity.Platform/CPU/Linux/x86_64/Fidelity.Libc.fidproj" }
image = { path = "../Fidelity.Image/CPU/Linux/x86_64/Fidelity.Image.Stb.fidproj" }
```

The consumer decides exactly which libraries it needs. The SourceResolver loads the
specified fidproj, matches the application's `open` declarations against the namespace
each source file provides, and only loads files whose namespaces are actually demanded.
Sources are collected in dependency-first order for CCS type-checking.

### Why Not Directory-Based Discovery?

A library directory contains more than just library source:

| Artifact | Role | Part of library? |
|----------|------|-------------------|
| `Fidelity.Platform.fidproj` | Hand-authored root manifest | Yes |
| `Fidelity.Libc.fidproj` | Farscape-generated sub-library | Yes (independently) |
| `pilot/libc.pilot.toml` | Farscape regeneration hook | No |
| `Bindings/Libc/Overlay/...` | Developer-owned Layer 3 | Yes (developer-managed) |

Directory-based discovery would sweep all of these into the dependency graph. File-based
targeting lets the consumer pick exactly what they need and leaves tooling artifacts,
regeneration hooks, and developer-owned code undisturbed.

### Composition Model

Farscape generates **one fidproj per pilot TOML invocation**. Library authors compose
parent fidproj files that reference sub-libraries as dependencies:

```
Fidelity.Platform/CPU/Linux/x86_64/
  Fidelity.Platform.fidproj           ← hand-authored root (Types, Console, etc.)
  Fidelity.Libc.fidproj              ← generated by Farscape
  Fidelity.Pthread.fidproj           ← generated by Farscape
  pilot/libc.pilot.toml              ← regeneration hook (not part of library)
  Bindings/Libc/...                  ← generated sources
```

Each fidproj is independently addressable. An application needing only libc bindings
references `Fidelity.Libc.fidproj` directly, without pulling in the full platform.

### Open-Driven Source Resolution

The `open` declaration in application source is the **demand signal** for source loading.
Just because a fidproj lists source files doesn't mean they get loaded — they are only
loaded when the application (or a transitive dependency) `open`s their namespace.

```
Application: open Fidelity.Image.Stb
                    ↓
SourceResolver: which fidproj dependency provides Fidelity.Image.Stb?
                    ↓
Fidelity.Image.Stb.fidproj → scan source files → module declarations match
                    ↓
Load only Stb source files (not Resvg, not full Fidelity.Image)
                    ↓
CCS type-checks only demanded sources in shared environment
```

**Resolution rules:**
- `open Fidelity.Image.Stb` → loads files whose module is `Fidelity.Image.Stb` or a child
- `open Fidelity.Image` → loads ALL files under the `Fidelity.Image` namespace (Stb AND Resvg)
- No `open` for a namespace → its source files are never loaded

**Namespace discovery**: Each `.clef` file declares its module on the first line
(`module Fidelity.Libc.IO`). A lightweight first-line scan extracts this — no full parse
needed. This is the namespace-to-file mapping.

**Design-time consideration**: An overly broad `open` (e.g., `open Fidelity.Image` when
only Stb is used) inflates the PSG unnecessarily. The language server (Lattice) should
surface this as a refinement suggestion — guiding users toward namespace specificity.
This is a "pit of success" design: the default works, but the tooling nudges toward
precision.

## Roadmap

### Near-term
- Implement `farscape verify` command
- Fix known TypeMapper and wrapper generation issues until core libraries pass
- Integrate verification into CI for Farscape's own test suite

### Medium-term
- `--verify` flag on `farscape project` for automatic post-generation check
- Machine-readable diagnostic output (JSON) for CI integration
- Verification status tracking across library versions

### Long-term (Atelier integration)
- Farscape's capabilities fold into Composer's **Transpose** feature (typed dynamic binding)
- Verification becomes part of Composer's library management, accessible through Atelier IDE
- `clefpak` packaging with verification as prerequisite gate
- Full algorithmic port capability via **Transcribe** (beyond FFI binding)
